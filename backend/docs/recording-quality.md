# Recording quality rules

Quality checks are opt-in. With no thresholds configured there is no new stream probe or quality report, and processing retains its existing behavior. Apply `core/src/main/resources/db/migrations/071_recording_quality.sql` after migrations 064 and 067 (it only depends on `processing_job` and `processing_attempt`, not on 072) before enabling this feature on an existing database. Migrations apply in filename order, so a fresh database runs 071 before 072. The Testcontainers schema is generated from the same migrations.

Spring configuration example (external application YAML):

```yaml
processor-quality:
  max-dropped-frames: 0
  drops-action: QUARANTINE
  min-duration-seconds: 60
  duration-action: WARN
  required-streams: [VIDEO, AUDIO]
  streams-action: QUARANTINE
  unavailable-action: WARN
```

Equivalent environment variables are `PROCESSORQUALITY_MAXDROPPEDFRAMES=0`, `PROCESSORQUALITY_DROPSACTION=QUARANTINE`, `PROCESSORQUALITY_MINDURATIONSECONDS=60`, `PROCESSORQUALITY_DURATIONACTION=WARN`, `PROCESSORQUALITY_REQUIREDSTREAMS=VIDEO,AUDIO`, `PROCESSORQUALITY_STREAMSACTION=QUARANTINE`, and `PROCESSORQUALITY_UNAVAILABLEACTION=WARN` (Spring relaxed binding removes hyphens). Optional numeric thresholds are absent by default; actions default to WARN. `FFPROBE_PATH` selects the existing ffprobe executable. A probe that fails to run (for example a wrong `FFPROBE_PATH`) or exits non-zero is logged at WARN and reported as an unavailable measurement, so with the default `unavailable-action: WARN` a broken ffprobe never quarantines anything. Watch for these warnings after enabling `required-streams`. Only a configured required-streams rule invokes the additional bounded, 60-second JSON stream probe.

**ARIB captions and `SUBTITLE`:** the stream rule trusts ffprobe's `codec_type`. Depending on the ffmpeg build, ARIB caption streams in Japanese broadcast TS are reported as `subtitle` (builds with ARIB caption support such as libaribcaption) or as `data`/`unknown` (older builds), and only `subtitle` counts. With `SUBTITLE` required and `streams-action: QUARANTINE`, a build of the second kind would hold every recording. Before requiring `SUBTITLE`, check `ffprobe -show_entries stream=codec_type -of json` on a known captioned recording with the configured `FFPROBE_PATH`, and start with `WARN`. ffprobe also uses its default probe size and analyze duration, so a stream that first appears late in the file (a sparse caption or secondary audio stream) can be missed and reported as `REQUIRED_STREAM_MISSING`. `unavailable-action` only covers a probe that fails or returns malformed output, not one that completes without seeing every stream.

`max-dropped-frames` is a nonnegative integer count, inclusive. `min-duration-seconds` is finite and positive, inclusive. Each failing rule chooses CONTINUE, WARN or QUARANTINE; the highest severity wins. Negative/unknown drops, nonpositive/nonfinite duration, and unavailable stream inspection are reported as unavailable, never treated as zero or as a pass. Unavailable measurements use the explicit `unavailable-action` policy, default WARN. Reports retain configured values, observed values, reason and action per rule.

Checks run after initial inspection and before registration, split, compression, NAS upload or encoder submission. Quarantine is an **in-place hold**: the original remains at its exact canonical source path. No file is moved or deleted. The job becomes QUARANTINED, with a completed QUALITY_CHECK stage but a FAILED attempt and QUALITY_QUARANTINED error. The report, the QUARANTINED transition and the attempt's FAILED outcome commit in one transaction, so a committed hold never leaves an ACTIVE attempt that would block release; if that transaction fails, the attempt is recorded as failed and the job is released as RETRYABLE like any other pre-registration failure. Repeated processing remains held even if configuration is changed, and each such run counts the existing hold, so a scheduled `process` over the same directory exits 4 on every pass until the hold is released. The log distinguishes a new hold (`Quality decision job=…`) from an existing one (`Job … remains quarantined in place …`). With any rule enabled, saving the quality report is part of processing: if the report cannot be written (for example a transient DB error), the recording fails before registration, even for a WARN or CONTINUE decision, and the job is left RETRYABLE for the next run. This is deliberate, because the write also re-verifies job ownership, but it is a new failure mode once the feature is turned on. Dry-run only inspects and prints the decision; it creates no job, report, file or artifact. A dry-run hold means “would quarantine,” not that a hold was persisted.

```sh
tvpcli quality report --job-id 42 --json
tvpcli quality release --job-id 42 --dry-run
tvpcli quality release --job-id 42          # confirms before changing state
tvpcli quality release --job-id 42 --yes    # explicit noninteractive confirmation
```

Report JSON has `schemaVersion: 1`, `jobId`, and `reports` with typed findings arrays, UTC timestamps, source identity and `quarantineLocation` for historical hold decisions. Reports are immutable and retained after release/reset (the table has no foreign key to the live job, on purpose). Nothing prunes them, and processing-history retention does not cover them; delete old `processing_quality_report` rows by `checked_at` manually if needed; use `status` to determine current job state. A known job without reports returns an empty array. An unknown job returns exit 3; invalid arguments return 2 and operational failure 1.

Release verifies QUARANTINED state, no active invocation/registration/callback, and an unchanged original; it atomically changes state to RETRYABLE. Dry-run checks the same current eligibility without prompting or mutation, and actual release revalidates after confirmation. Refusal returns exit 4 with a reason code: `NOT_QUARANTINED`, `ACTIVE_ATTEMPT`, `SOURCE_CHANGED` or `CHANGED_CONCURRENTLY` (the job changed between validation and update). Other failures are operational errors (exit 1). The identity is the #64 canonical path + byte size + last-modified timestamp fingerprint, **not a content hash**: same-size content changes with a restored timestamp cannot be detected. A source can also change after validation; keep recordings stable during retry. Release does not automatically process the file and does not bypass a still-failing policy: processing it again under an unchanged policy starts a new attempt, records a new report and quarantines it again (the release output says so too). Change the policy (or accept the recording another way) before releasing if it should go through.

Known limitations: release revalidates the fingerprint and then changes state, but the file check is not atomic with the state update, so a change in between is not detected. `source_path` is stored and printed verbatim in reports; treat it like any other recording path if reports are ever forwarded to a web UI or Slack.

Batch processing continues after each held or failed recording. If any recording is held (including dry-run quality decisions), `process` returns exit 4; otherwise ordinary failures return 1 and success/skips 0. Existing completed/submitted jobs remain skips. A path that does not exist or a directory that cannot be listed also counts as a failure (exit 1); before quality rules, `process` logged and notified Slack but still exited 0, so wrappers that relied on that should check their inputs. WARN decisions are not counted separately: they are logged and kept in the report, and the recording counts as processed. Interruption follows [graceful shutdown](graceful-shutdown.md): no later recording is started and the CLI exits 130. A stop during the stream probe interrupts ffprobe and records the attempt as INTERRUPTED; a probe timeout or failure is an unavailable measurement handled by `unavailable-action`.

`scripts/quality-cli-smoke.py` runs the packaged CLI end to end against a disposable MariaDB container (Docker and a prebuilt `processor:console:bootJar` required). It is a manual check and does not run in CI or `./gradlew test`.
