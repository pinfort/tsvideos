# 検証付きの processor アップロード

processor を起動する前に、`064_processing_job.sql`、続いて `072_upload_manifest.sql` をデプロイする。既存の環境にも新規の環境にも両方のマイグレーションが必要で、テスト用スキーマにはすでに含まれている。デプロイ中は古い processor を停止すること。既存の `created_file` の行は、検証済みの所有の証拠にはならず、暗黙には引き継がれない。

圧縮済みの元ファイルとコールバックの出力は、どちらも `VerifiedUploadCommand` を使う。その永続的な `upload_manifest` は、ジョブ/成果物、NAS 上の正確な宛先、ソースの正規パス/サイズ/更新時刻/SHA-256、一意な一時ファイル名、検証ポリシー、クレーム、登録済みファイル ID を識別する。宛先の所有はジョブをまたいで一意である。既定のリモートチェックは存在とサイズで、ストリーミングによる SHA-256 の読み戻しには `processor.upload.verify-sha256=true` (環境変数 `PROCESSOR_UPLOAD_VERIFY_SHA256=true`) を設定する。**トレードオフ:** 既定では、ローカルファイル (生録画の唯一のコピーである圧縮済みの元ファイルを含む) は、NAS とのサイズ一致を確認した後に削除される。書き込んだバイト列はストリーミング中にハッシュされ、記録されたソースの SHA-256 と一致しなければならないが、NAS が保存したバイト列を黙って壊す場合は、読み戻しを有効にしたときにしか検出できず、その代償として検証のたびに SMB 経由で各成果物を 1 回読み直すことになる。未対応または失敗したチェックサムの読み取りはアップロードを失敗させ、黙ってダウングレードすることはない。ソースの SHA-256 は常に記録され、サイズと更新時刻が同じ置き換えも含め、ローカル削除の前に再チェックされる。

順序: NEW を永続化 -> CREATING -> 一時ファイルを排他的にオープン -> TRANSFERRING -> 送信したバイト列の SHA-256 を記録済みのソースと比較し、一時ファイルを検証 -> TEMP_VERIFIED -> FINALIZING を永続化 -> 同一共有内での置き換えなしのリネーム -> 最終ファイルを検証 -> FINALIZED -> トランザクションで created_file + REGISTERED -> リモートとローカルのフィンガープリントを再検証 -> ローカルを削除。対応するリモートが永続的に登録されるまで、ローカルの出力は削除されない。ローカルファイルの削除に失敗した場合は REGISTERED のままとなり、同一のコールバックで再試行できる。中断されたコールバックは、#64 のコールバックのクレームのルールを維持する。

SMB の実装は、jcifs の `createNewFile()` (排他的ではない) ではなく、共有なしの O_CREAT | O_EXCL を明示的に使う。リネームには `renameTo(target, false)` を使う。Samba SMB2 の統合テストで、同一共有内のリネームと置き換えが起きないことを確認しているが、これはあらゆる NAS/ファイルシステムでのクラッシュ耐久性を保証するものではない。共有をまたぐコピーは使わない。リネームの前後でネットワーク障害やプロセスのクラッシュが起きると、結果が不明になることがある。既存の宛先のサイズやチェックサムが一致していても、それは今回の起動がそれを所有している証拠には決してならない。

## 復旧と一時ファイルのクリーンアップ

processor/コールバックのクラッシュ後は、すべての processor/コールバックのプロセスを停止し、`tvpcli release-claim <original-recording-path>` を実行する。これはそのジョブのクレーム済みアップロード (状態、NAS、最終パス、トークン) を一覧し、確認を求めたうえで、まさにそれらのトークンだけをクリアする。状態の変更や NAS への操作は行わないため、次の実行では再開されるか、必要な整合が報告される。`--dry-run` は一覧のみを行う。一覧後に引き継がれたクレームは解放されない。

手動での復旧 SQL (先にすべての processor/コールバックのプロセスを停止し、行をバックアップし、必ず正確な `id` を指定すること):

```sql
-- Inspect one job's uploads.
SELECT id, state, claim_token, updated_at, final_path, temporary_path FROM upload_manifest WHERE job_id = ?;
-- Release a claim left by a crashed/killed process.
UPDATE upload_manifest SET claim_token = NULL, updated_at = UTC_TIMESTAMP(6) WHERE id = ? AND claim_token = ?;
-- CREATING whose temporary file you have deleted/quarantined after inspection.
UPDATE upload_manifest SET state = 'NEW', updated_at = UTC_TIMESTAMP(6) WHERE id = ? AND state = 'CREATING' AND claim_token IS NULL;
```

- アクティブなマニフェストのクレームが同時に存在する場合、他の起動は拒否される。リースの期限切れによって、以前のプロセスが死んだと見なすことはない。プロセスのクラッシュ後は、放棄された `claim_token` を確認/クリアする前にすべての processor/コールバックのプロセスを停止し、それを含む処理/コールバックのジョブも #64 の手順で整合させること。
- NEW は名前を予約しただけの状態。CREATING は、排他的な作成が成功した可能性も失敗した可能性もあることを意味する。再試行で CREATING が自動的に NEW に戻るのは、マニフェストの一意な一時パスが存在しない場合のみ (例: オープンの前に共有やディレクトリの作成が失敗した場合)。古い、あるいは遅れた作成があっても、次の排他的オープンは失敗し、それを引き継ぐことはない。一時パスが存在する場合、そのパスは自動では削除されない。不確かなファイルを削除/隔離して行を NEW に戻す前に、NAS/サーバーの監査の証拠を確認すること。
- TRANSFERRING は、排他的オープンが成功したことの証明になる。通常の再試行では、変更のないローカルのソースを検証し、所有している正確なその一時パスだけを削除してから再試行する。TEMP_VERIFIED では、同じ一時成果物を検証して確定できる。`cleanupTemporary(jobId, artifact)` は、所有が証明されたこれらの一時ファイルだけを明示的に削除し、その行を NEW に戻す。NEW では何もしない。これは今後の復旧ツール向けの core の復旧 API であり、経過時間に基づく自動スイープではない。
- FINALIZING は、意図的に自動再試行がブロックされる。processor を停止している間に、NAS のリネーム/監査の証拠を確認すること。リネームが完了したと証明できる場合は、FINALIZED にする前に、最終ファイルのサイズ/チェックサム/ソースの同一性を検証する。実行されていないと証明でき、所有している一時ファイルが検証済みのバイト列のまま残っていて最終ファイルが存在しない場合は、TEMP_VERIFIED に戻す。所有を確認できない場合は、両方のコピーを保持し、手作業で解決する。同じサイズのファイルがあるというだけで FINALIZED にしてはならない。
- FINALIZED の再試行では、再アップロードせずにリモートの検証と DB の登録をやり直す。REGISTERED の再試行では、ローカルのクリーンアップの前に、関連する DB レコードとリモートの成果物を検証する。リモートファイルが欠落/破損/アクセス不能の場合は、ローカルのデータを保持し、復元/整合が必要になる。
- reset はまず、クレーム、曖昧な成果物、未登録の最終成果物が失われないことを検証する。program の削除後、アップロードマニフェストが廃止されるのは、最終ターゲットが存在しないことが確認され、所有している正確な一時ファイルがクリーンアップされた後のみ。DB/NAS の失敗により RESETTING の証拠が残ることがある。所有権の行を捨てずに、手動の復旧のために保存しておくこと。

コールバックの完了時に生録画と分割入力を削除する前に、processor は、登録済みの元アーカイブのレシートと、生録画の #64 のパス/サイズ/更新時刻のフィンガープリントを再チェックする。検証済みの元レシートを持たない従来のジョブは、元ファイルを保持し、ERROR を報告する。メタデータからレシートを捏造してはならない。アーカイブが新しい経路で再アップロード/検証されるか、所有の証拠とともに独立して整合されるまで、ローカルの元ファイルを保持すること。生ファイルのバージョンのフィンガープリントは、生ファイルの内容全体のハッシュではない。#64 でのその本来の意味を維持すること。

不確かな外部の副作用からの自動復旧はなく、SMB と MariaDB が分散トランザクションを構成するという主張もしない。手動での復旧の前には、書き込み側を停止すること。テーブルのタイムスタンプだけでは、オーナーが死んでいる証拠にならない。手動で編集する前にデータベースの行をバックアップし、クリーンアップはマニフェストの正確なパスだけに限定すること。

NAS のターゲットは、事前にエンコードされた URL ではなく、共有からの相対パスそのものである。呼び出し側は宛先のパスを URL エンコードしてはならない。jcifs はそれらをそのまま解決する (パーセントデコードやフラグメントの解析はない) ため、`#` や `%` のようなタイトルの文字はそのまま保存される。先頭の `/`、バックスラッシュ、空/`.`/`..` のセグメント、`:` (NTFS の代替データストリーム)、`?` (ワイルドカード)、制御文字は、所有権を確保する前に、説明付きの `IllegalArgumentException` で拒否される。`destination_key` は宛先の文字列そのものをハッシュするが、SMB サーバーは通常、名前を大文字小文字を区別せずに比較し、末尾のドットや空白を取り除くことがあるため、2 つのキーが 1 つのファイルを指す場合がある。これで何かが上書きされることはない (最終パスの存在チェックと、置き換えなしのリネームの両方が既存のファイルを見て、"Unowned final destination exists" で失敗する) が、そのような衝突は、重複した宛先として検出されるのではなく、整合が必要になる。

`reset <original-recording-path>` が program/executed の行を削除した*後*に失敗した場合 (例: マニフェストの廃止中に NAS にアクセスできなくなった)、NAS/DB へのアクセスを復旧し、通常の確認付きで**同じ reset コマンドをもう一度**実行する。正規化された入力パスから、永続的な RESETTING のジョブが見つかる。復旧の経路では、executed/program/split の行が存在しないこと、コールバックのクレームがないこと、関連する created_file の行がすべて存在しないこと、最終的な NAS のターゲットがすべて存在しないことが確認されている必要がある。そのうえで、所有が証明された一時成果物だけをクリーンアップし、マニフェストとジョブを廃止する。`--dry-run` は、この保留中の復旧を変更なしで報告する。いずれかのチェックが失敗した場合は、証拠が残り、パスは推測されない。分割パスのメタデータが失われている場合、残っているローカルの分割ファイルは、警告とともに手動での確認のために保持される。元の録画は常に保持される。program の削除自体が NAS で部分的に失敗した場合は、その DB レコードが残っていることがある。DB のロールバックがリモートのバイト列を復元したと仮定せず、まずその正確なターゲットを復元/整合させること。
