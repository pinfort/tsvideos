# Verified processor uploads

Deploy `064_processing_job.sql` and then `072_upload_manifest.sql` before starting any processor. Existing installations and new installations need both migrations; test schema already includes them. Stop old processors during deployment. Existing `created_file` rows do not prove verified ownership and are not silently adopted.

Both compressed originals and callback outputs now use `VerifiedUploadCommand`. Its durable `upload_manifest` identifies a job/artifact, exact NAS destination, source canonical path/size/mtime/SHA-256, unique temporary name, verification policy, claim and registered file ID. Destination ownership is unique across jobs. The default remote check is existence/size; set `processor.upload.verify-sha256=true` (environment `PROCESSOR_UPLOAD_VERIFY_SHA256=true`) for streaming SHA-256 readback. **Trade-off:** with the default, the local file (including the compressed original, the only copy of the raw recording) is deleted after a size match against the NAS. The bytes written are hashed while streaming and must equal the recorded source SHA-256, but a NAS that silently corrupts stored bytes is only caught with readback enabled, at the cost of re-reading every artifact over SMB once per verification. Unsupported/failed checksum reading fails the upload; it never downgrades silently. Source SHA-256 is always recorded and rechecked before local deletion, including same-size/mtime replacements.

Order: persist NEW -> CREATING -> exclusive temporary open -> TRANSFERRING -> compare the SHA-256 of the bytes sent with the recorded source, verify temporary -> TEMP_VERIFIED -> persist FINALIZING -> non-replacing same-share rename -> verify final -> FINALIZED -> transactional created_file + REGISTERED -> reverify remote and local fingerprint -> delete local. No local output is deleted before its remote counterpart is durably registered. Failure deleting a local file keeps REGISTERED so the identical callback can retry. Interrupted callbacks retain the #64 callback claim rules.

The SMB implementation explicitly uses O_CREAT | O_EXCL with no sharing, not jcifs `createNewFile()` (which is not exclusive). Rename uses `renameTo(target, false)`. Samba SMB2 integration tests demonstrate one-share rename and no replacement; this is not a guarantee of crash durability for every NAS/filesystem. No cross-share copy is used. A network failure or process crash around rename may leave an unknown result. Size/checksum equality of an existing destination is never proof that this invocation owns it.

## Recovery and temporary cleanup

After a processor/callback crash, stop every processor/callback process and run `tvpcli release-claim <original-recording-path>`. It lists the job's claimed uploads (state, NAS, final path, token), asks for confirmation and clears exactly those tokens; it never changes a state or touches the NAS, so the next run resumes or reports the reconciliation needed. `--dry-run` only lists them. A claim taken over after the listing is not released.

Manual recovery SQL (stop every processor/callback process first, back up the row, and always match the exact `id`):

```sql
-- Inspect one job's uploads.
SELECT id, state, claim_token, updated_at, final_path, temporary_path FROM upload_manifest WHERE job_id = ?;
-- Release a claim left by a crashed/killed process.
UPDATE upload_manifest SET claim_token = NULL, updated_at = UTC_TIMESTAMP(6) WHERE id = ? AND claim_token = ?;
-- CREATING whose temporary file you have deleted/quarantined after inspection.
UPDATE upload_manifest SET state = 'NEW', updated_at = UTC_TIMESTAMP(6) WHERE id = ? AND state = 'CREATING' AND claim_token IS NULL;
```

- A concurrent active manifest claim rejects other invocations. No lease expiry assumes the previous process died. After a process crash, stop all processor/callback processes before inspecting/clearing an abandoned `claim_token`; also reconcile the enclosing processing/callback job under the #64 procedure.
- NEW has only reserved a name. CREATING means exclusive creation may or may not have succeeded. A retry returns CREATING to NEW automatically only when the manifest's unique temporary path is absent (for example the share or directory creation failed before the open); a stale or late creation then makes the next exclusive open fail instead of being adopted. If the temporary path exists, its path is never removed automatically: inspect NAS/server audit evidence before deleting/quarantining the uncertain file and returning the row to NEW.
- TRANSFERRING proves exclusive open succeeded. A normal retry verifies the unchanged local source, removes only this exact owned temporary path, then retries. TEMP_VERIFIED can verify and finalize the same temporary artifact. `cleanupTemporary(jobId, artifact)` explicitly removes only these proven owned temporary files and returns their row to NEW; NEW does nothing. It is a core recovery API for subsequent recovery tooling, not an automatic age-based sweep.
- FINALIZING is deliberately blocked for automatic retry. Inspect NAS rename/audit evidence while processors are stopped. If the rename is proven completed, verify final size/checksum/source identity before setting FINALIZED. If proven not performed, and the owned temporary still exists with verified bytes and final is absent, return to TEMP_VERIFIED. If ownership cannot be established, preserve both copies and resolve manually. Never set FINALIZED just because a same-sized file exists.
- FINALIZED retries remote verification and DB registration without re-upload. REGISTERED retries validate the associated DB record and remote artifact before local cleanup. Missing/corrupt/inaccessible remote files retain local data and require restoration/reconciliation.
- Reset first validates that claims/ambiguous/unregistered final artifacts cannot be lost. After program deletion, upload manifests are retired only after their final targets are confirmed absent and exact owned temporary files are cleaned. DB/NAS failures can leave RESETTING evidence; preserve it for manual recovery instead of dropping ownership rows.

Before removing raw recordings and split inputs at callback completion, the processor rechecks the registered original archive receipt and the raw recording's #64 path/size/mtime fingerprint. Legacy jobs lacking a verified original receipt preserve originals and report ERROR. Do not manufacture a receipt from metadata: retain local originals until the archive has been re-uploaded/verified through the new path or independently reconciled with ownership evidence. The raw version fingerprint is not a full raw-file content hash; preserve its original semantics from #64.

There is no automatic recovery from uncertain external effects and no claim that SMB and MariaDB form a distributed transaction. Stop writers before manual recovery; table timestamps alone do not prove an owner is dead. Back up database rows before manual edits and restrict any cleanup to exact manifest paths.

NAS targets are raw share-relative paths, not pre-encoded URLs; callers must not URL-encode destination paths. jcifs resolves them literally (no percent-decoding or fragment parsing), so title characters such as `#` and `%` are stored as-is. Leading `/`, backslashes, empty/`.`/`..` segments, `:` (NTFS alternate data streams), `?` (wildcard) and control characters are rejected with a descriptive `IllegalArgumentException` before allocating ownership.

If `reset <original-recording-path>` fails *after* deleting the program/executed rows (for example NAS becomes inaccessible during manifest retirement), restore NAS/DB access and run the **same reset command again**, with its normal confirmation. The canonical input path finds the durable RESETTING job. The recovery path requires the executed/program/split rows to be absent, no callback claim, every associated created_file row absent, and every final NAS target confirmed absent. It then cleans only proven owned temporary artifacts and retires the manifests/job. `--dry-run` reports this pending recovery without mutations. If any check fails, evidence remains and no path is guessed. Lost split-path metadata means remaining local split files are preserved with a warning for manual inspection; the original recording is always preserved. If program deletion itself failed partially at the NAS, its DB records may remain: restore/reconcile those exact targets first rather than assuming the DB rollback restored remote bytes.
