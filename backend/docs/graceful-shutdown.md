# processor の中断と復旧

processor CLI は、協調的な 1 回の起動を所有する。SIGINT / Ctrl-C と SIGTERM は停止を要求し、オーナーを割り込み、以降のパス/ファイルの受け付けを止める。協調的な中断を捕捉した場合は終了コード 130 で終了する。JVM のネイティブなシグナルによるシャットダウンでは、ネイティブの終了ステータス (SIGTERM では一般に 143) が残る場合がある。Windows サービスのラッパーは、通常の JVM シャットダウンシグナルを転送する必要がある。taskkill /F、SIGKILL、電源断、JVM のクラッシュでは、クリーンアップを実行できない。

`PROCESSOR_SHUTDOWN_GRACE_SECONDS` (`processor.shutdown.grace-seconds`) の既定値は 30 で、1 から 300 の整数を受け付ける。1 つの期限が、起動の完了待ちと Spring のクローズの両方を対象とする。期限の最後の 5 分の 1 はクローズ用に確保されるため、起動に割り当てられるのは猶予の 80% である。標準の Spring シャットダウンフックは、この CLI でのみ無効化されている。代わりのフックは、オーナーが中断を記録している間 DB コンテキストを利用可能に保つ。ドライバがブロックされた場合や、協調しない処理があると、猶予を使い切ることがある。その場合 JVM は、クリーンアップや永続化の完了を保証せずに終了する。残った ACTIVE の試行は手作業で確認すること。コンテキストの破棄はデーモンスレッドで実行され、フックを無期限に延長することはない。

`processing.api.ProcessingCancellation` (#164 より前は `core.component`) は `runOwned`、`requestStop`、`check`、および時間制限付きの `awaitStopped` を公開する。コーディネーターがサポートするオーナーは 1 回の起動につき 1 つだけで、完了後は再利用できない。将来の並列ワーカー (#69) には、複数オーナーのライフサイクルの明示的なサポートが必要になる。`ProcessingHistoryCommand.stage` は外部処理の前後でキャンセルをチェックし、その進捗コールバックは呼び出しごとにチェックする。履歴のトランザクションは短いまま保たれる。INTERRUPTED とマークされるのは、現在所有している試行 (アクティブなステージを含む) のみ。復旧処理は、DB アクセスのためにスレッドの割り込みフラグを一時的にクリアし、その後復元する。他の起動に属する古い試行が死んでいると推測されることは決してない。

ツールのサブプロセスは ProcessHandle の子孫として追跡され、割り込みやタイムアウト時には穏当な終了、続いて強制終了が行われる。正常終了した後は、ツールが意図的に残した子プロセスには触れない。ストリームの読み出しにはデーモンスレッドと時間制限付きの待機を使い、stdout/stderr を継承する子孫も含む。追跡できるのは、直接のプロセスが生きている間に観測された子孫のみ。これは ProcessHandle のサンプリングであり、OS のプロセスグループや Windows の Job Object ではない。親の終了直前に起動された子は、意図的に切り離されていなくても、観測前にリペアレントされることがある。そのような観測されなかった子孫は生き残る可能性があるが、パイプの読み出しは引き続き時間制限される。ツールは自分の子を待つべきであり、より強い封じ込めにはプロセスグループによる監督が必要になる。意図的に祖先関係から逃れた切り離しプロセスはこの契約の対象外で、CLI が実行ファイル名で kill することは決してない。エンコーダサーバー自体は管理対象ではない。投入前のキャンセルは投入を阻止する。投入の境界に入った後のキャンセルは、エンコーダが実際にタスクを受け付けていた場合でも、オペレーターによる整合のために SUBMISSION_UNKNOWN を残す。これは [processing-idempotency.md](processing-idempotency.md) の SUBMISSION_UNKNOWN の手順 (エンコーダ側でタスクを確認し、ジョブを SUBMITTED または REJECTED にする) で解決する。

元の入力、登録済みのレシート、確定済みまたは曖昧な NAS 成果物は保持される。削除されるのは、TRANSFERRING/TEMP_VERIFIED にある、排他的に所有するアップロードの一時パスのみ。CREATING/FINALIZING は、安全に削除できるという根拠にはならない。クリーンアップに失敗した場合、マニフェストは保持され、失敗に添付される。圧縮は CREATE_NEW を使い、この起動が取得した不完全な出力は失敗時に削除される。すでに存在していた出力は保持される。分割が中断された場合は、ファイル名のプレフィックスだけでは所有を証明できないため、その出力と登録は保持される。reset や再試行の前に、`status --json` / `history --json`、アップロードマニフェスト、外部のエンコーダの状態を確認すること。この変更は、ジョブを自動的に取り戻したり、エンコーダへの投入を再送したりはしない。

この PR と #71 はどちらも FileProcessingPipeline を拡張している。両者を統合する際は、エンコーダ投入前後の明示的なチェックに加えて、QUALITY_CHECK を `history.stage` 経由で維持し、このキャンセルの境界を観測できるようにすること。

`scripts/smoke_graceful_shutdown.py` は、使い捨ての MariaDB コンテナに対して、パッケージ済みの CLI へ実際の SIGTERM を送る (Linux、Docker、Java 24 の `JAVA_HOME`、事前にビルドした jar が必要)。これは手動チェックであり、CI や `./gradlew test` では実行されない。
