# Bulk recording operations

Selection covers only the displayed page (maximum 100). Changing filters or page clears selection. Preview shows program/executed/split/created records, original recording paths, NAS files and exact move destinations. Applying requires explicit confirmation. Failed targets still on the current page remain selected, successful targets are deselected and the library refreshes.

Only COMPLETED programs with FILE_MOVED artifacts are eligible. ERROR does not prove that an encoder callback stopped. Shared executed records or normalized NAS path aliases are refused, including case, slash and trailing-dot/space aliases. Estimated reclaimed bytes are registered metadata, not a physical-space guarantee. Neither action deletes the original local recording or local split files. Delete removes their database records through the existing core command.

`POST /api/v1/programs/bulk/preview` accepts `{ "ids": [1,2], "action": "DELETE" }`, or `MOVE` with a `directory` label. The existing normalization and base/index/program hierarchy are retained; separators, traversal, URI delimiters, control characters and ambiguous trailing dots are refused, both before and after normalization. Bulk actions also refuse existing files whose NAS paths contain `: ? # %` or trailing dots/spaces; those remain deletable through the single-program paths, because the NAS layer only refuses traversal, blank segments, control characters and `:` (jcifs resolves `#`, `%` and `?` literally). A MOVE target without generated files is refused rather than reported as a no-op success. Existing registered targets, unchanged paths and duplicate proposed destinations are refused. Unregistered NAS collisions are rejected atomically by exclusive creation at apply.

`POST /api/v1/programs/bulk/apply` accepts `{ "request": <preview.request>, "fingerprints": { "1": "<fingerprint>", ... } }`. SHA-256 fingerprints cover action, normalized destination, complete metadata and shared references. Changes including added/removed artifacts require another preview. Invalid input returns HTTP 400; batches return per-target SUCCESS, FAILED, STALE or NOT_FOUND. Fingerprints are concurrency checks, not authentication tokens; existing deployment access controls still apply. Web calls use Next Server Actions and the server-side API base URL used by search.

Each target has an independent database transaction. Locks cover program/executed/split records and created-file aliases to prevent additions between comparison and mutation. Alias safety currently scans and locks the created-file table because paths are text and SMB aliases are case-insensitive. NAS operations retain these locks, so while one target is being moved or deleted, every other `created_file` insert waits — including `after-encode` registering new outputs, which fails (leaving that program in `ERROR`) if the wait exceeds the server's `innodb_lock_wait_timeout`. **Do not run bulk apply while `process` or `after-encode` may be running**, and keep MOVE selections small: apply is a single synchronous HTTP request that copies, reads back and verifies every file, so a large selection can also outlive proxy or client timeouts (a timed-out client should re-preview to see what completed). The bulk side waits at most 10 seconds for this lock and reports the target as FAILED instead of queueing indefinitely. No automatic cleanup or retention policy is introduced.

NAS changes cannot roll back with the database. Moves exclusively create a destination, copy, verify size and SHA-256 by readback, then re-stat a fresh source handle before source deletion. Copy/verification failures retain the source and may leave a partial destination for inspection. That destination is never registered, so a retry fails exclusive creation until it is removed: confirm the source still exists with its registered size, then delete only the destination copy by hand. Occupied targets are never overwritten. Do not concurrently mutate files through external SMB writers: these checks cannot provide a distributed transaction. A later artifact or DB commit failure can leave earlier NAS files moved/deleted while DB records roll back. FAILED explicitly reports this possibility; the cause is logged with the program ID. Inspect the preview paths and reconcile before retrying; never delete the only remaining copy to make a retry succeed.

Tests cover stale snapshots, real MariaDB locks and transactional failures, local original preservation, real Samba exclusive creation and successful verified moves, simulated corruption/collision/read failures, API validation and UI selection/confirmation/cancellation. Docker is required, including `ghcr.io/servercontainers/samba:latest` used by the development stack.
