# 録画の一括操作

選択対象は表示中のページ (最大 100 件) のみ。フィルタやページを変更すると選択は解除される。プレビューでは program / executed / split / created の各レコード、元録画のパス、NAS 上のファイル、移動先の正確なパスを確認できる。適用には明示的な確認が必要。適用に失敗した対象のうち現在のページに残っているものは選択されたままになり、成功した対象は選択解除され、ライブラリが再読み込みされる。

対象になるのは、FILE_MOVED の成果物を持つ COMPLETED の program のみ。ERROR は、エンコーダのコールバックが止まったことの証明にならない。共有された executed レコードや、正規化後に同一になる NAS パスのエイリアス (大文字小文字、スラッシュ、末尾のドット/空白の違いを含む) は拒否される。`estimatedMetadataBytes` は対象ファイルの登録サイズで、DELETE なら解放される量、MOVE なら転送される量を表す。これは登録済みメタデータであり、物理的な空き容量を保証するものではない。どちらの操作もローカルの元録画やローカルの分割ファイルは削除しない。Delete は既存の core のコマンドを通じて、それらのデータベースレコードを削除する。

`POST /api/v1/programs/bulk/preview` は `{ "ids": [1,2], "action": "DELETE" }`、または `directory` ラベル付きの `MOVE` を受け付ける。既存の正規化と base/index/program の階層は維持される。区切り文字、トラバーサル、URI 区切り文字、制御文字、曖昧な末尾のドットは、正規化の前後どちらでも拒否される。一括操作は、NAS パスに `: ? # %` や末尾のドット/空白を含む既存ファイルも拒否する。ただしそれらは、NAS 層がトラバーサル・空のセグメント・制御文字・`:` だけを拒否する (jcifs は `#`・`%`・`?` をそのまま解決する) ため、単一 program 向けの経路では引き続き削除できる。生成ファイルを持たない MOVE 対象は、何もしない成功として扱わず拒否される。登録済みの既存対象、変更のないパス (SMB は大文字小文字を区別しないため、大文字小文字だけの変更を含む)、重複した移動先の提案も拒否される。未登録のものとの NAS 上の衝突は、適用時の排他的作成によってアトミックに拒否される。

`POST /api/v1/programs/bulk/apply` は `{ "request": <preview.request>, "fingerprints": { "1": "<fingerprint>", ... } }` を受け付ける。SHA-256 のフィンガープリントは、アクション、正規化後の移動先、完全なメタデータ、共有参照を対象とする。成果物の追加/削除を含む変更があった場合は、再度プレビューが必要になる。不正な入力は HTTP 400 を返す。バッチは対象ごとに SUCCESS、FAILED、STALE、NOT_FOUND を返す。フィンガープリントは並行実行チェック用であり、認証トークンではない。既存のデプロイ環境のアクセス制御が引き続き適用される。Web からの呼び出しは Next Server Actions と、検索で使うサーバー側の API ベース URL を使う。

各対象は独立したデータベーストランザクションで処理される。ロックは program / executed / split のレコードと created_file のエイリアスを対象とし、比較から変更までの間の追加を防ぐ。パスがテキストで SMB のエイリアスが大文字小文字を区別しないため、エイリアスの安全性確認は現状 created_file テーブルをスキャンしてロックする。NAS 操作中もこれらのロックは保持されるため、ある対象の移動・削除中は、他のすべての `created_file` の INSERT が待たされる。これには新しい出力を登録する `after-encode` も含まれ、待機がサーバーの `innodb_lock_wait_timeout` を超えると失敗し、その program は `ERROR` になる。**`process` や `after-encode` が実行中の可能性がある間は、一括適用を実行しないこと。** また MOVE の選択は小さく保つこと。適用は単一の同期 HTTP リクエストで、すべてのファイルをコピー・読み戻し・検証するため、選択が大きいとプロキシやクライアントのタイムアウトを超える場合もある (タイムアウトしたクライアントは、再プレビューして完了した内容を確認すること)。一括操作側がこのロックを待つのは最大 10 秒 (catalog の `LedgerLocks.lockCreatedFiles` が実行する `BulkLibraryMapper.lockFiles` の MariaDB 固有の `SET STATEMENT innodb_lock_wait_timeout = 10 FOR ...`。データベースを変える場合は見直すこと) で、無期限にキューイングせず、その対象を FAILED として報告する。自動クリーンアップや保持ポリシーは導入していない。

`tvmcli cleanup apply` (backend の README を参照) は、この適用のガード付きバリエーションを使う。`lockFiles` の後、さらにすべての `program`、`executed_file`、`splitted_file` の行を、この順のテーブル順で、同じ 10 秒の待機でロックする。これらのロック下で、各対象の削除前にレビュー済みプラン全体 (重複検出または保持期間のスキャンと、残りの対象の完全なプレビュー) を再生成する。そのため 100 件のプランでは、ライブラリのロック中に最大 100 回のライブラリ全体の再計算が行われる。これは、すべてのコピーを削除してしまいかねない逆向きの keep プランを拒否するためのコストである。クリーンアップは、他に誰もライブラリへ書き込んでいないときに実行すること。ビジー状態の場合、対象は変更されないまま FAILED ("Library is busy") と報告される。

NAS の変更はデータベースとともにロールバックできない。移動は、移動先を排他的に作成し、コピーし、読み戻しでサイズと SHA-256 を検証し、移動元の削除前に新しいハンドルで移動元を再 stat する。コピー・検証・移動元削除の失敗時は、移動元を残し、その移動が排他的に作成した移動先を削除する。その際、新しいハンドルで移動元が変更されていないことを再確認するため、再試行が妨げられることはない。移動元を確認できない場合 (変更された、消えた、NAS に到達できない)、移動先がただ一つのコピーである可能性があるため残し、エラーをログに出す。その場合は、どちらのコピーが完全かを確認してから、もう一方を手作業で削除すること。各移動は、単純なコピーより 2 回多くファイルを読む (コピーとチェックサムの読み戻し)。使用済みの移動先は決して上書きされない。外部の SMB 書き込みクライアントから並行してファイルを変更しないこと。これらのチェックは分散トランザクションにはならない。同じ録画の後続ファイルの移動に失敗した場合、移動済みのファイルは同じ検証付き移動で (新しいものから順に) 元に戻される。戻しに失敗した場合はログに出力され、そのファイルは移動先に残る。削除は元に戻せない。すでに両方の NAS ストアから無くなっている登録済みファイルの削除は、設計上エラーであり、削除済みとはみなさない。設定ミスや到達不能な共有があると、実際には存在するファイルのデータベース行まで削除してしまうためである。そのため、部分的に削除された後の再試行は、すでに削除されたファイルで失敗し、それらの行は手作業で整合させる必要がある。すべての NAS 手順が成功した後の DB コミット失敗は補償されないため、DB レコードがロールバックされる一方で、NAS ファイルは移動/削除されたままになる可能性がある。NAS 層は `:` (SMB のストリーム区切り) を拒否するが、これはそもそも保存されるファイル名に現れない。FAILED はこの可能性を明示的に報告し、原因は program ID とともにログに出力される。プレビューのパスを確認し (`tvmcli verify` は、NAS 上で欠落している、またはサイズが異なる登録済みファイルを報告する)、再試行の前に整合させること。再試行を成功させるために、唯一残ったコピーを削除してはならない。

テストでは、古くなったスナップショット、実際の MariaDB のロックとトランザクション失敗、ローカルの元ファイルの保全、実際の Samba での排他的作成と検証付き移動の成功、模擬的な破損・衝突・読み取り失敗、API の検証、UI の選択・確認・キャンセルを扱う。Docker が必要で、開発用スタックが使う `ghcr.io/servercontainers/samba:latest` も含まれる。
