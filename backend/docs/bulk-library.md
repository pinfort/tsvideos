# 録画の一括操作

選択対象は表示中のページ (最大 100 件) のみ。フィルタやページを変更すると選択は解除される。プレビューでは program / executed / split / created の各レコード、元録画のパス、NAS 上のファイル、移動先の正確なパスを確認できる。適用には明示的な確認が必要。適用に失敗した対象のうち現在のページに残っているものは選択されたままになり、成功した対象は選択解除され、ライブラリが再読み込みされる。

対象になるのは、FILE_MOVED の成果物を持つ COMPLETED の program のみ。ERROR は、エンコーダのコールバックが止まったことの証明にならない。共有された executed レコードや、正規化後に同一になる NAS パスのエイリアス (大文字小文字、スラッシュ、末尾のドット/空白の違いを含む) は拒否される。`estimatedMetadataBytes` は対象ファイルの登録サイズで、DELETE なら解放される量、MOVE なら転送される量を表す。これは登録済みメタデータであり、物理的な空き容量を保証するものではない。どちらの操作もローカルの元録画やローカルの分割ファイルは削除しない。Delete は catalog の既存の協調削除 (`ProgramCommand.delete`) を通じて、それらのデータベースレコードを削除する。`BulkLibraryCommand` 自体は library モジュールにある (#158)。

`POST /api/v1/programs/bulk/preview` は `{ "ids": [1,2], "action": "DELETE" }`、または `directory` ラベル付きの `MOVE` を受け付ける。既存の正規化と base/index/program の階層は維持される。区切り文字、トラバーサル、URI 区切り文字、制御文字、曖昧な末尾のドットは、正規化の前後どちらでも拒否される。一括操作は、NAS パスに `: ? # %` や末尾のドット/空白を含む既存ファイルも拒否する。ただしそれらは、NAS 層がトラバーサル・空のセグメント・制御文字・`:` だけを拒否する (jcifs は `#`・`%`・`?` をそのまま解決する) ため、単一 program 向けの経路では引き続き削除できる。生成ファイルを持たない MOVE 対象は、何もしない成功として扱わず拒否される。登録済みの既存対象、変更のないパス (SMB は大文字小文字を区別しないため、大文字小文字だけの変更を含む)、重複した移動先の提案も拒否される。未登録のものとの NAS 上の衝突は、適用時の排他的作成によってアトミックに拒否される。

`POST /api/v1/programs/bulk/apply` は `{ "request": <preview.request>, "fingerprints": { "1": "<fingerprint>", ... } }` を受け付ける。SHA-256 のフィンガープリントは、アクション、正規化後の移動先、完全なメタデータ、共有参照を対象とする。成果物の追加/削除を含む変更があった場合は、再度プレビューが必要になる。不正な入力は HTTP 400 を返す。バッチは対象ごとに SUCCESS、FAILED、STALE、NOT_FOUND を返す。フィンガープリントは並行実行チェック用であり、認証トークンではない。既存のデプロイ環境のアクセス制御が引き続き適用される。Web からの呼び出しは Next Server Actions と、検索で使うサーバー側の API ベース URL を使う。

各対象は独立したデータベーストランザクションで処理される。ロックは program / executed / split のレコード、対象の created_file 行、対象が触るパス (元のパスと MOVE の移動先) のエイリアスを対象とし、比較から変更までの間の追加を防ぐ (#112)。

- **パスの正規化キー**: catalog の `CreatedFilePathKey` が、区切り文字 (`\` と `/`) の統一、各セグメント末尾のドット/空白の除去、大文字小文字の畳み込み (NFC 合成の後、Java の Unicode 全体の対応で大文字化してから小文字化) をしたキーを作る。SMB が同じファイルとみなすパスは同じキーになる (逆に NAS が区別するパスを同じキーにすることはあるが、それは拒否や待機が増えるだけ)。NFC/NFD など合成の違いも同じキーにする。キーの SHA-256 を `created_file.path_key` (索引付き、一意ではない) に保存する。長いパスもハッシュなので索引の長さに影響しない。
- **パスごとのガード**: `created_file_path_guard` (キーごとに 1 行、主キーだけ、削除しない) の行を主キーの upsert でロックする。catalog の `created_file` のパスの書き込み (`CreatedFileCatalog.register` の INSERT、`CreatedFileCommand.recordMove` のパス変更) はすべて、書き込むパスのガードを先に取る。一括適用は対象トランザクションの最初に、対象が触るすべてのパスのガードをキー順に取る (`LedgerLocks.lockCreatedFilePaths`)。そのため適用中は、それらのパスやそのエイリアスへの登録・移動は commit まで待たされ、別のパスへの書き込みは待たない (ガードは主キーのレコードロックで、ギャップロックを取らない)。待たされた書き込みは適用の commit 後に通常どおり実行される (拒否ではなく直列化。commit 後の状態はその後のプレビューと適用が改めて検査する)。
- **対象の split のガード**: `created_file` には `splitted_file` への外部キーがないため、パスのガードだけでは、対象の program の split に別のパスで新しいファイルが登録されるのを止められない (DELETE ならその行が孤児として残り、MOVE ならそのファイルを取りこぼしたまま SUCCESS になる)。そこで同じテーブルに split ごとのキー (`CreatedFilePathKey.splitGuard`、パスのキーと衝突しない前置き付きの SHA-256) を置き、一括適用はパスのガードと一緒に対象の全 split のガードをキー順に取る。`CreatedFileCatalog.register` も、書くパスと登録先 split の 2 つのガードを同じキー順に取ってから INSERT し、その後 split を共有ロック付きで読み直す (`LOCK IN SHARE MODE`。最新の commit を見る)。split が消えていれば (待っている間に削除が commit された) 自分の行を消して `IllegalStateException` で拒否するので、孤児の行は残らない。共有ロックは登録の commit まで split の削除を止める。登録は INSERT まで台帳の行ロックを持たないため、全件ロックを取るガード付き cleanup ともデッドロックしない。別の録画の split への登録は待たない。
- **単独の移動 (manager console の `Modify`)**: `ProgramCommand.moveCreatedFiles` をトランザクションの外から呼ぶと、自分のトランザクション (`REPEATABLE_READ`) を開き、最初の NAS 操作の前に一括適用と同じ順序で、元のパスと移動先のガードと program の split のガード → 対象の created_file 行 → program のグラフをロックする。その後ファイルと split を読み直し、計画したものと違えば (待っている間に一括適用などが変更した) NAS を触らずに `IllegalStateException` で拒否する。一括適用から呼ばれたときは対象トランザクションに参加し、取得済みのロックをもう一度取るだけになる。そのため単独の移動と一括適用は互いに待ち合い (一括側の待機は最大 10 秒で FAILED)、移動中も別のパスや別の録画の登録は待たない。
- **順序と鮮度**: 対象のパスは対象トランザクションの前に別の読み取りトランザクションで読む (`REPEATABLE_READ` のスナップショットはトランザクション最初の通常の読み取りで決まるため、ガードの前に読むと、ガードを取る直前に commit された別名の行を見落とすことがある)。トランザクション内ではガード → 対象の created_file 行 (主キーのレコードロック) → program / executed / split の順にロックし、その後に読み直す。読み直したファイルやパスがガードの範囲外 (その間に追加・改名された) なら STALE を返す。エイリアスの検査はこれらのパスだけを索引で引く (`LedgerSnapshots.createdFilesAt`)。テーブル全体を対象ごとに読むことはなく、プレビューも選択全体のパスを 1 回引くだけになった。
- **MOVE の DB 更新は NAS 移動の後**: `ProgramCommand.moveCreatedFiles` は、その program のすべての NAS 移動を終えてから行の `file` / `path_key` を更新する。`file` の更新は長い UNIQUE (`USING HASH`) の検査を伴い、その索引のロックが commit まで残りうるため、先に更新すると残りの転送の間、無関係な INSERT を待たせる可能性があるため。行の更新に失敗した場合も、移動済みのファイルを新しいものから順に戻してから例外を送出する。
- **`path_key` の埋め戻し**: migration 076 より前の行と、catalog を通さない SQL で書いた行は `path_key` が NULL のまま。プレビューと適用は開始時に、それらを短い独立したトランザクションで 500 行ずつ埋める (`CreatedFileCatalog.fillMissingPathKeys`)。他のトランザクション (実行中の移動や一括適用) がロックしている行は待たずに飛ばし (`FOR UPDATE SKIP LOCKED`)、次のプレビュー/適用で埋める。そのためプレビューは行ロックを待たない (書き込むのは `path_key` だけで、他の列や結果は変えない)。失敗してもログに出すだけで、NULL の行は索引を使わずにパスを比較して検査に含めるので、安全性は変わらない (遅くなるだけ)。cleanup の `plan` / dry-run は自分の読み取りトランザクションの中でプレビューするため埋め戻しをせず (`previewInTransaction`)、DB に書き込まない。

**前提**: すべての `created_file` のパスの書き込みが catalog を通ること。ガードはアプリケーションの規約で、DB の制約ではない。SQL で直接 `created_file` に書き込む作業 (行の追加や `file` の変更) はガードを取らないため、一括適用や単独の移動と同時に行わないこと (DB への直接の保守作業は、manager と processor を止めてから行う)。直接書いた行の `path_key` は NULL になるか古くなりうる。NULL なら上のとおり埋め戻されるが、`file` だけを書き換えた行は `path_key` を NULL に戻しておくこと。また processor (`after-encode`) をこの変更より古いビルドのまま manager だけを更新しないこと (古いビルドはガードを取らない)。ガードは行の追加・移動を直列化するだけで、NAS 上の未登録ファイルとの衝突は、従来どおり排他的作成で防ぐ。

これにより、一括適用の NAS 操作中も、無関係なパスの `after-encode` の登録は待たされない。同じパスやそのエイリアスへの登録だけが、適用の commit まで (最大でサーバーの `innodb_lock_wait_timeout` まで) 待つ。また MOVE の選択は小さく保つこと。適用は単一の同期 HTTP リクエストで、すべてのファイルをコピー・読み戻し・検証するため、選択が大きいとプロキシやクライアントのタイムアウトを超える場合もある (タイムアウトしたクライアントは、再プレビューして完了した内容を確認すること)。一括操作側がロックを待つのは最大 10 秒 (catalog の `LedgerLocks` が実行する `BulkLibraryMapper` の MariaDB 固有の `SET STATEMENT innodb_lock_wait_timeout = 10 FOR ...`。データベースを変える場合は見直すこと) で、無期限にキューイングせず、その対象を FAILED として報告する。program / executed / split のロック (`lockSplits` / `lockReferences` は索引の範囲をロックする) はこれまでどおりで、この変更の対象外。自動クリーンアップや保持ポリシーは導入していない。

`tvmcli cleanup apply` (backend の README を参照) は、この適用のガード付きバリエーションを使う。パスのガードの後、対象の行だけでなく `created_file` の全行をロックし (`lockFiles`、全件スキャンの next-key ロック。保持中は `created_file` の INSERT がすべて待たされる)、さらにすべての `program`、`executed_file`、`splitted_file` の行を、この順のテーブル順で、同じ 10 秒の待機でロックする。これらのロック下で、各対象の削除前にレビュー済みプラン全体 (重複検出または保持期間のスキャンと、残りの対象の完全なプレビュー) を再生成する。そのため 100 件のプランでは、ライブラリのロック中に最大 100 回のライブラリ全体の再計算が行われる。これは、すべてのコピーを削除してしまいかねない逆向きの keep プランを拒否するためのコストである。クリーンアップは、他に誰もライブラリへ書き込んでいないときに実行すること。ビジー状態の場合、対象は変更されないまま FAILED ("Library is busy") と報告される。

NAS の変更はデータベースとともにロールバックできない。移動は、移動先を排他的に作成し、コピーし、読み戻しでサイズと SHA-256 を検証し、移動元の削除前に新しいハンドルで移動元を再 stat する。コピー・検証・移動元削除の失敗時は、移動元を残し、その移動が排他的に作成した移動先を削除する。その際、新しいハンドルで移動元が変更されていないことを再確認するため、再試行が妨げられることはない。移動元を確認できない場合 (変更された、消えた、NAS に到達できない)、移動先がただ一つのコピーである可能性があるため残し、エラーをログに出す。その場合は、どちらのコピーが完全かを確認してから、もう一方を手作業で削除すること。各移動は、単純なコピーより 2 回多くファイルを読む (コピーとチェックサムの読み戻し)。使用済みの移動先は決して上書きされない。外部の SMB 書き込みクライアントから並行してファイルを変更しないこと。これらのチェックは分散トランザクションにはならない。同じ録画の後続ファイルの移動に失敗した場合、移動済みのファイルは同じ検証付き移動で (新しいものから順に) 元に戻される。戻しに失敗した場合はログに出力され、そのファイルは移動先に残る。削除は元に戻せない。すでに両方の NAS ストアから無くなっている登録済みファイルの削除は、設計上エラーであり、削除済みとはみなさない。設定ミスや到達不能な共有があると、実際には存在するファイルのデータベース行まで削除してしまうためである。そのため、部分的に削除された後の再試行は、すでに削除されたファイルで失敗し、それらの行は手作業で整合させる必要がある。すべての NAS 手順が成功した後の DB コミット失敗は補償されないため、DB レコードがロールバックされる一方で、NAS ファイルは移動/削除されたままになる可能性がある。NAS 層は `:` (SMB のストリーム区切り) を拒否するが、これはそもそも保存されるファイル名に現れない。FAILED はこの可能性を明示的に報告し、原因は program ID とともにログに出力される。プレビューのパスを確認し (`tvmcli verify` は、NAS 上で欠落している、またはサイズが異なる登録済みファイルを報告する)、再試行の前に整合させること。再試行を成功させるために、唯一残ったコピーを削除してはならない。

テストでは、古くなったスナップショット、実際の MariaDB のロックとトランザクション失敗 (NAS 移動の途中で無関係なパスの登録が commit され、元のパスと移動先のエイリアスの登録・移動が待たされること、プレビュー後に現れたエイリアスで STALE になること、対象の split への登録が待たされ、削除の後では孤児を残さず拒否されること、単独の移動と一括適用が NAS 操作の前に待ち合うこと、パスの索引が使われること。catalog の `CatalogTransactionTest` と library の `BulkLibraryApplyTest`。migration 076 の再実行と既存行の扱い、ロック中の行を飛ばす埋め戻しは catalog の `CreatedFileCatalogTest`)、ローカルの元ファイルの保全、実際の Samba での排他的作成と検証付き移動の成功、模擬的な破損・衝突・読み取り失敗、API の検証、UI の選択・確認・キャンセルを扱う。Docker が必要で、開発用スタックが使う `ghcr.io/servercontainers/samba:latest` も含まれる。
