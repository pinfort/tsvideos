# Processing attempts, status and history

Apply the migrations in filename order (`064_processing_job.sql`, `067_processing_history.sql`, `072_upload_manifest.sql`) before deploying; 067 has no foreign keys, so it only needs `processing_job` (064) to exist. The existing processing_job is the only live job identity/claim. `processing_history_identity` retains its immutable ID, version fingerprint and path plus an attempt counter; it is not a second queue or claim mechanism. History has no cascade to live jobs or generated files, so reset retains diagnostics.

`tvpcli status [--job-id ID | --all] [--json]` reports current job state, latest invocation and all active invocations. `tvpcli history [--job-id ID | --all] [--json]` reports immutable identity, attempts and ordered stages. No selector means all. A PROCESS attempt COMPLETED means submission was acknowledged, not that encoding finished: the job remains SUBMITTED while waiting for its CALLBACK. Retired jobs display RETIRED and retain their attempts. Existing jobs with no new attempts show that explicitly. JSON is one UTF-8 schemaVersion 1 object with `jobs` or `attempts`; enum values are strings and IDs/counts are numbers. Logs go to stderr. Exit codes: 0 success/empty, 1 operational failure, 2 invalid arguments, 3 explicitly requested missing job, 130 interrupted read.

Each PROCESS/CALLBACK invocation has a monotonically increasing per-job attempt number and ACTIVE, COMPLETED, FAILED or INTERRUPTED outcome. Stage names are INSPECT, SPLIT, COMPRESS, UPLOAD_ORIGINAL, SUBMIT_ENCODER, UPLOAD_ENCODED and FINALIZE. Stage events carry start/end UTC timestamps, outcome, static errorCode and generated artifact references. FINALIZE may appear for individual local cleanup and for final program completion. Known encoder-failure callbacks record a failed FINALIZE with ENCODER_FAILURE without copying external messages. Invalid paths that cannot form a #64 input identity, legacy callbacks without a known job, rejected duplicate claims and dry runs do not invent a new job/history identity. Inspection failures after a successfully owned claim are retained before safe retryable rollback.

## Activity and interrupted owners

All history timestamps are UTC wall clock (independent of local recording timestamps), serialized explicitly with Z. `activityAt` updates at stage boundaries and throttled progress heartbeats (at most once per 10 seconds); tool stages without progress update at their boundaries. It is evidence of the last recorded activity, not proof that the process still runs or died. There is no automatic reclaim or timeout-based INTERRUPTED transition. A caught interruption records INTERRUPTED; process termination/power loss may leave ACTIVE evidence across restart. Inspect and stop the owner before using the existing #64/#72 reconciliation procedures and explicitly finishing the history attempt INTERRUPTED. Merely starting a new process must never declare an older attempt dead.

## Core API for recovery and monitoring

`ProcessingHistoryCommand.begin(job, PROCESS|CALLBACK)` returns a durable attempt; the same existing job must already be owned under #64 rules. `startStage`, `finishStage`, `finish`, `heartbeat` and `progress` store activity using short REQUIRES_NEW transactions. `stage(attemptId, stage, artifactMapper) { work }` deliberately executes work outside its DB transactions and records a sanitized failure before rethrowing. `failed` classifies exceptions into fixed codes; arbitrary messages, causes and stack traces are never stored. `finish(attemptId, INTERRUPTED, INTERRUPTED)` is available to explicitly reconciled recovery tooling after the owner is known stopped. `history(jobId?)` and `status(jobId?)` are consistent repeatable-read snapshots. Artifact types identify INPUT, SPLITTED_FILE, UPLOAD_MANIFEST or PROGRAM; referenced live rows can later disappear and history remains diagnostic evidence, not authority to delete a file or repeat an external effect. #72 receipts continue to govern deletion.

## Retention

No implicit retention job is enabled. Review and explicitly execute `core/src/main/resources/db/maintenance/processing_history_cleanup.sql` to remove terminal attempts older than 90 days (change its UTC cutoff deliberately if needed). The script deletes terminal stage rows and terminal attempts transactionally, retains ACTIVE evidence (an attempt with a stuck ACTIVE stage is kept until it is explicitly finished), and keeps identity/counter rows so numbers cannot be reused. It is separate from schema migrations and covered by a real MariaDB test. Back up history before cleanup if needed for diagnosis. Paths and artifact references are operational data; control database/CLI access accordingly.
