# 処理の試行・状態・履歴

デプロイ前に、マイグレーションをファイル名の順 (`064_processing_job.sql`、`067_processing_history.sql`、`072_upload_manifest.sql`) に適用する (MariaDB のみ: DDL は DATETIME 列に `DEFAULT UTC_TIMESTAMP(6)` を使う)。067 は外部キーを持たないため、`processing_job` (064) が存在していればよい。既存の processing_job が、唯一の現行のジョブ識別/クレームである。`processing_history_identity` は、変更不可の ID、バージョンのフィンガープリント、パス、および試行カウンタを保持する。これは 2 つ目のキューやクレームの仕組みではない。履歴から現行のジョブや生成ファイルへのカスケードはないため、reset しても診断情報は残る。

`tvpcli status [--job-id ID | --all] [--json]` は、現在のジョブの状態、最新の起動、およびすべてのアクティブな起動を報告する。`tvpcli history [--job-id ID | --all] [--json]` は、変更不可の識別情報、試行、順序付きのステージを報告する。セレクタを指定しない場合は全件を対象とする。PROCESS の試行が COMPLETED とは、投入が受理されたことを意味し、エンコードが完了したことではない。ジョブは CALLBACK を待つ間 SUBMITTED のままになる。廃止されたジョブは RETIRED と表示され、その試行は保持される。新しい試行がない既存のジョブは、その旨が明示的に表示される。JSON は UTF-8 の schemaVersion 1 のオブジェクト 1 つで、`jobs` または `attempts` を持つ。列挙値は文字列、ID と件数は数値で表される。ログは stderr に出力される。終了コード: 0 は成功/空、1 は操作上の失敗、2 は引数が不正、3 は明示的に指定されたジョブが存在しない、130 は読み取りの中断。引数が不正な場合はすべての `tvpcli` サブコマンドで 2 で終了する (以前は Clikt の既定の 1 だった)。そのため、特定の非ゼロコードを判定するラッパーは 2 を受け入れる必要がある。`jobState` の `RETIRED` は合成された値で、現行の `processing_job` の行が (例えば reset で) 削除され、履歴だけが残っていることを示す。出力には録画と NAS のパスが含まれるため、`--json` の出力を取得した場合はデータベースと同様に扱うこと。

PROCESS/CALLBACK の各起動には、ジョブごとに単調増加する試行番号と、ACTIVE、COMPLETED、FAILED、INTERRUPTED のいずれかの結果がある。ステージ名は INSPECT、SPLIT、COMPRESS、UPLOAD_ORIGINAL、SUBMIT_ENCODER、UPLOAD_ENCODED、FINALIZE。ステージイベントは、開始/終了の UTC タイムスタンプ、結果、固定の errorCode、生成された成果物への参照を持つ。FINALIZE は、個々のローカルのクリーンアップと、最終的な program の完了の両方で現れることがある。既知のエンコーダ失敗のコールバックは、外部のメッセージをコピーせずに、ENCODER_FAILURE を伴う失敗した FINALIZE を記録する。#64 の入力識別を構成できない不正なパス、既知のジョブを持たない従来のコールバック、拒否された重複クレーム、ドライランでは、新しいジョブ/履歴の識別情報は作られない。クレームを正しく所有した後の検査の失敗は、安全で再試行可能なロールバックの前に保持される。

## アクティビティと中断されたオーナー

すべての履歴のタイムスタンプは UTC の壁時計時刻 (ローカルの録画時刻とは独立) で、Z を付けて明示的にシリアライズされる。`activityAt` は、ステージの境界と、間引かれた進捗ハートビート (10 秒に 1 回まで) で更新される。進捗のないツールのステージは、その境界で更新される。これは最後に記録されたアクティビティの証拠であり、プロセスがまだ動いている、あるいは死んだことの証明ではない。自動での取り戻しや、タイムアウトに基づく INTERRUPTED への遷移はない。中断を捕捉した場合は INTERRUPTED が記録される。プロセスの終了や電源断では、再起動後も ACTIVE の証拠が残ることがある。既存の #64/#72 の整合手順を使い、履歴の試行を明示的に INTERRUPTED で終了させる前に、オーナーを確認して停止すること。新しいプロセスを起動しただけで、古い試行が死んでいると宣言してはならない。

## 復旧と監視のための Core API

`ProcessingHistoryCommand.begin(job, PROCESS|CALLBACK)` は永続的な試行を返す。同じ既存のジョブが、#64 のルールの下ですでに所有されている必要がある。`startStage`、`finishStage`、`finish`、`heartbeat`、`progress` は、短い REQUIRES_NEW トランザクションでアクティビティを保存する。`stage(attemptId, stage, artifactMapper) { work }` は、意図的に DB トランザクションの外で処理を実行し、再スローの前に無害化した失敗を記録する。`failed` は例外を固定のコードに分類し、任意のメッセージ、原因、スタックトレースは保存されない。`finish(attemptId, INTERRUPTED, INTERRUPTED)` は、オーナーが停止したと分かった後、明示的に整合された復旧ツールが利用できる。`history(jobId?)` と `status(jobId?)` は、一貫した repeatable-read のスナップショットである。成果物の種類は INPUT、SPLITTED_FILE、UPLOAD_MANIFEST、PROGRAM を識別する。参照されている現行の行は後で消える可能性があり、履歴は診断上の証拠であって、ファイルを削除したり外部の副作用を繰り返したりする権限を与えるものではない。削除は引き続き #72 のレシートに従う。

## 保持

暗黙の保持ジョブは有効になっていない。90 日より古い終端状態の試行を削除するには、`core/src/main/resources/db/maintenance/processing_history_cleanup.sql` を確認したうえで明示的に実行する (必要なら UTC のカットオフを意図的に変更すること)。このスクリプトは、終端状態のステージ行と終端状態の試行をトランザクション内で削除し、ACTIVE の証拠 (ACTIVE のまま止まったステージを持つ試行は、明示的に終了されるまで保持される) を残し、番号が再利用されないよう識別/カウンタの行を維持する。スキーマのマイグレーションとは別になっており、実際の MariaDB のテストでカバーされている。診断に必要な場合は、クリーンアップの前に履歴をバックアップすること。パスと成果物への参照は運用データであるため、データベースと CLI へのアクセスはそれに応じて管理すること。
