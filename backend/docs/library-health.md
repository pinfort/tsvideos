# ライブラリの状態と保存済みの検証結果

このバージョンをデプロイする前に (新規・既存のどちらの環境でも)、アプリケーションデータベースへ `core/src/main/resources/db/migrations/051_library_health.sql` を適用する。このリポジトリはスキーマのマイグレーションを自動では実行しない。このマイグレーションが作るのは名前空間付きの `health_verification_run` と `health_verification_finding` だけで、録画には手を加えない。

`GET /api/v1/health/library` は、処理失敗 (`ERROR`) の番組、既知の正のドロップ数を持つ番組、保存済みの検証状態を読む。孤立した番組 (録画が見つからない番組) も表示する。NAS にはアクセスしない。`POST /api/v1/health/library/verify` は CLI の verify と同じ `LibraryVerificationCommand` を明示的に呼び、更新後の状態を返す。web の `/health` ページはブラウザからのリクエストに同一オリジンの Next ルートを使い、バックエンドへのリクエストは `frontend/lib/api/health` に残す。広い CORS 許可は追加しない。

このアプリは LAN 内で使う前提で、他の API (番組の削除や一括操作を含む) と同じく認証はない。API や Next ルートに到達できる相手は誰でもスキャンを始められる。同時に実行できるスキャンは 1 つだけで (409)、スキャンは読み取り専用である。Next ルートは別オリジンからの POST (`Origin` が `x-forwarded-host` または `host` と一致しないもの) を 403 で拒否し、別のサイトがブラウザ経由でスキャンを始めることを防ぐ。Next ルートの応答は、409 (別のスキャンが実行中)、502 (バックエンドがエラーを返した)、504 (バックエンドに到達できない、またはタイムアウト。スキャンが続いている可能性がある) を区別する。

スキャンは存在とサイズの読み取りだけを行い、ファイルの修復・削除はしない。5 つの検証結果は変わらない: VERIFIED、MISSING、SIZE_MISMATCH、INACCESSIBLE、UNCHECKED。NAS にアクセスできないことは、ファイルが欠落している証拠ではない。転送未完了のレコードや成果物のない番組は UNCHECKED になる。これら個々の結果は完了したスキャンの正当な結果であり、実行全体の失敗とは、検証または保存を最後まで行えなかったことを意味する。

実行の開始・完了時刻とファイルごとの確認時刻は、マイクロ秒精度の UTC で明示的に保存する。スキャンはまず RUNNING のクレームをコミットし、データベースのトランザクションの外で NAS I/O を行い、変更されない検証結果と COMPLETED の状態をまとめてアトミックにコミットする。実行中のスキャンはプロセスをまたいで 1 つだけ許される (一意な active marker)。同時の POST は 409 を返す。POST はスキャンの後で状態を読み直して返すが、この 2 つはアトミックではないため、その間に別のスキャンが始まると、応答の `latestRun` は今実行した実行ではなく新しい実行を指すことがある。

実行全体の失敗には安全な `VERIFICATION_FAILED` コードだけを記録し、前回完了したスナップショットを残す。原因はデータベースではなく manager:api のログに書く。`POST` はこの場合も 200 を返し、`latestRun.state` が `FAILED` になる。失敗の記録そのものが失敗した場合は 1 度だけ再試行し、それでも失敗すると実行は RUNNING のまま残るため、下記の手動復旧が必要になる。ログに実行 ID が出る。また、検証結果の `reason` は 255 文字を超えると切り詰めて保存し、長いエラーメッセージで実行全体が失敗しないようにする。完了したスキャンがないとき、GET が健全な結果を作り出すことはない: summary と lastCompletedRun は null のまま。失敗中・実行中の新しい実行は、前回完了した結果とは別に表示する。

ページには UTC の完了時刻、経過時間、ファイルごとの確認時刻を表示する。削除済みの番組の結果はそうとわかるラベルを付けて詳細へのリンクを省き、過去の結果と件数は残す。結果は過去のものであり、その後のファイルシステムの変化は反映しない。ページやプロセスを再読み込みしても結果は消えない。

検証は同期的に実行される。Next ルートはバックエンドの応答を待つが、Node の fetch (undici) は既定で応答ヘッダーを 300 秒までしか待たない。大きなライブラリでこれを超えたりブラウザが切断したりすると、画面には「検証が継続している可能性があります」と表示されるが、サーバー側のスキャンは続いている。失敗とみなさず、「状態を再読み込み」で実行中かどうかを確かめること。

スキャンは manager:api のリクエストの中で実行されるため、再起動・デプロイ・クラッシュでプロセスが止まると、実行が active marker 付きの RUNNING のまま残る。manager:api は起動時に、残っている RUNNING の実行をすべて `FAILED` (`failure_code` = `INTERRUPTED`) にして解放する。古いかどうかでは判断せず、起動時点で他にスキャンを持つプロセスがないことを前提にしている。複数の manager:api インスタンスが同じデータベースを共有する構成では、他のインスタンスの実行中のスキャンを解放してしまうため、`tsvideos.health.reconcile-on-startup=false` で無効にすること。起動時にデータベースへ接続できなかった場合は警告をログに出して起動を続け、解放は行わない。既定で有効なので、デプロイ時に新旧のインスタンスが重なる場合も同じことが起きる: 古いインスタンスのスキャン中に新しいインスタンスが起動すると、その実行は INTERRUPTED になる。このとき古いスキャンの完了処理は RUNNING でない実行を完了できずにロールバックされ、警告をログに出す。失われるのはそのスキャンの結果だけで、前回完了した結果や新しいスキャンには影響しない。

起動時の解放が無効、または失敗した場合は手動で復旧する。409 のメッセージもこの手順を指す。まずスキャンを持つプロセスを停止し終了を確認してから、実行 ID を確認し、オペレーターがその実行だけを明示的に失敗にしてよい:

```sql
-- 123 を確認した中断済みの実行 ID に置き換える。そのプロセスを停止してから実行すること。
UPDATE health_verification_run
SET state = 'FAILED', completed_at = UTC_TIMESTAMP(6),
    failure_code = 'VERIFICATION_FAILED', active_marker = NULL
WHERE id = 123 AND state = 'RUNNING';
```

これで前回完了したスナップショットが置き換わることはない。過去の実行と検証結果は残り、自動での削除 (pruning) はない。このブランチには処理のアクティビティ時刻を永続的に記録する仕組みがないため、処理の停滞検出は含まない。
