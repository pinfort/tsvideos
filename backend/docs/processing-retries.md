# Bounded retries for verified uploads

Only `VerifiedUploadCommand.upload`, `register`, and `verifyRegistered` use the shared retry executor. Split/compression, encoder submission, local/remote deletion, explicit cleanup/reset, and the whole pipeline are never retried automatically. A dry-run performs no upload mutation or retry.

```yaml
processor-retry:
  max-attempts: 3        # total attempts including the first, range 1..10
  initial-delay-millis: 250
  max-delay-millis: 5000
```

Delays must be positive, maximum at least initial and both at most 60000 ms. An out-of-range value fails application startup rather than being clamped. The processor, manager API and manager console all bind these keys through their `@ConfigurationPropertiesScan` of `me.pinfort.tsvideos.core.config`. Backoff doubles to the cap, with bounded jitter from half the cap to the full cap. There is no separate wall-clock cap: total backoff is bounded by `(max-attempts - 1) × max-delay-millis`, at most 9 minutes with the largest allowed settings. The wait uses `Thread.sleep`, which is acceptable for the CLI but should be revisited before reusing the executor on web request threads. Each wait is interruptible; cancellation is checked before attempts and before/after backoff. Retry logs contain only operation, static classification, attempt counts and delay, never exception text or configuration. Final errors propagate unchanged for existing per-recording history/Slack handling; individual retries do not notify Slack. Callback processing failures are reported once and then rethrown, producing exit status 1 (behavior change: earlier builds exited 0 after reporting, so Amatsukaze's post-batch now sees the failure); interruption retains exit status 130. Notification, history or claim-release failures are suppressed on the original callback failure.

Only typed connection/timeouts (`SocketTimeoutException`, `ConnectException`, `NoRouteToHostException`, `SQLTransientConnectionException`, including bounded nested causes) qualify. Generic IO errors are not guessed from text. Permission/authentication, missing files, invalid input, nontransient SQL, interruption and corruption/state failures do not qualify, nor does any failure carrying a suppressed `RetryRefusedException`, which marks a failed cleanup or unconfirmed claim release. Other suppressed exceptions (for example close failures) do not block a retry. Permanent types take precedence over a nested transient exception anywhere in the chain, so a transient cause wrapped by, for example, an `IllegalArgumentException` or `SecurityException` is never retried; this deliberately prefers a missed retry.

A transient error alone is insufficient. The durable upload manifest must exist, be unclaimed, and remain in a safe state both before and after backoff. Upload accepts NEW/TRANSFERRING/TEMP_VERIFIED/FINALIZED/REGISTERED; registration accepts FINALIZED/REGISTERED; receipt validation requires REGISTERED. Each new attempt claims the row again. CREATING/FINALIZING are ambiguous and require manual reconciliation; another owner's claim is never taken over.

A TRANSFERRING retry removes only the proven-owned temporary artifact, then retransfers from the unchanged source. It cannot overwrite an unrelated final path. A cleanup failure stops immediately. Claim release must affect exactly one owned row; release errors are suppressed on the primary failure and forbid retry. Successful explicit retirement deletes its token-owned manifest and therefore needs no separate release. Manifest reads, claims, state transitions, releases and retirement use short REQUIRES_NEW transactions. CREATING and FINALIZING are committed before the corresponding NAS effect, and NAS operations run outside database transactions. This also avoids stale snapshots in a suspended Spring transaction with auto-commit disabled. Registration remains one atomic transaction and repeated receipts converge to the same created-file row. Remote checks are repeated before permitted local removal; original recordings are not deleted by this retry executor.

This branch uses the verified #70/#67/#72/#64 stack. #63 recovery is independent and must preserve the same claim/release and safe-state rules when integrated. No new schema migration is required.

`backend/scripts/retry-cli-smoke.py` runs the packaged processor jar (`processor/console/build/libs/console.jar`, build it first) against a dedicated MariaDB and a Samba container that it stops and restarts mid-upload. The packaged smoke intentionally lacks an original archive receipt: upload retries and encoded registration succeed, but final callback completion fails safely with exit 1 and leaves the original intact. This is not a successful callback completion.
