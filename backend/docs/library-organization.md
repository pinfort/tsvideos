# Manual collections and tags

Apply `core/src/main/resources/db/migrations/053_library_organization.sql` to the existing application database before deploying this branch, for example `mariadb <database> < 053_library_organization.sql`. Back up the database first. The existing `program` table must use InnoDB with signed BIGINT `id` (the supplied application schema does). This migration adds only `library_collection`, `library_collection_program`, `library_tag`, and `library_tag_program`. It does not access broadcast/emergency tag tables from other features. The Testcontainers initialization schema includes the same definitions.

Names are trimmed and normalized to Unicode NFC, must contain 1–100 UTF-16 code units without control characters, and preserve display casing. Uniqueness uses NFC text lowercased with `Locale.ROOT`, stored using binary collation. Thus `Café`, decomposed `Café`, and `CAFÉ` denote the same name. Collection and tag names have separate namespaces. Explicit duplicate creation/rename returns 409; assigning a tag by name reuses an existing normalized name. Unknown object or program IDs return 404. Assignment/unassignment is idempotent and protected by row locks and unique pair keys.

Collection and tag removal deletes metadata/associations only. It never removes a program, original recording or NAS artifact. Foreign keys cascade associations when an existing recording deletion removes its program, including both current mapper deletion paths. Read queries join existing programs so inconsistent legacy association rows cannot create broken recording entries. All organization changes are database-only; there is no NAS access or inferred series membership.

The web management page is `/collections`; recording detail pages assign/unassign collections and tags and can create a tag by name. Removal requires confirmation stating that recordings remain. Browse links use shared search with recording date ascending and ID ascending as the tie-breaker. Library search preserves `collectionId` and `tagId` in the URL, combines them with other filters, and uses the same predicates for total count and page items. A saved filter for an already removed ID returns zero results.

API: `GET/POST /api/v1/library/{collections|tags}`, `GET/PUT/DELETE /api/v1/library/{kind}/{id}`, `PUT/DELETE /api/v1/library/{kind}/{id}/programs/{programId}`, `GET /api/v1/programs/{programId}/organization`, and `POST /api/v1/programs/{programId}/tags`. Creation, rename and tag-by-name accept `{ "name": "..." }`. Mutations from the web use same-origin Next Server Actions. Existing deployment access controls still apply.
