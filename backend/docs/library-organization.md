# Manual collections and tags

Apply `core/src/main/resources/db/migrations/053_library_organization.sql` to the existing application database before deploying this branch, for example `mariadb <database> < 053_library_organization.sql`. Back up the database first. The existing `program` table must use InnoDB with signed BIGINT `id` (the supplied application schema does). This migration adds only `library_collection`, `library_collection_program`, `library_tag`, and `library_tag_program`. The Testcontainers schema and `docker-compose.test.yml` are generated from / mount the same migration file.

**Manual tags are not detector tags.** `library_tag` holds operator-managed names. The existing `executed_file_tag` table (`ExecutedFileTag`, e.g. `ews`, `superimpose`) holds tags that detectors attach to recordings automatically, keyed by `executed_file_id`; it is exposed as `tags` on `GET /api/v1/programs/{id}`. The two never share rows, IDs or names: a manual tag may be called `ews` without affecting detection, and deleting a manual tag or its associations never touches `executed_file_tag`/`executed_file_check`. To keep them apart in the API, manual tags use `libraryTagId` (search) and `/library-tags` (tag-by-name); the UI calls them 手動タグ.

Names are trimmed and normalized to Unicode NFC, must contain 1–100 UTF-16 code units without control characters, and preserve display casing. Uniqueness uses NFC text lowercased with `Locale.ROOT` (not full Unicode case folding, so `ß` and `SS` stay distinct), stored using binary collation in `name_key` (VARCHAR(200), since lowercasing can lengthen a name). Thus `Café`, decomposed `Café`, and `CAFÉ` denote the same name. Collection and tag names have separate namespaces. Explicit duplicate creation/rename returns 409; assigning a tag by name reuses an existing normalized name. Unknown object or program IDs return 404. Assignment/unassignment is idempotent and protected by row locks and unique pair keys. Assignment and tag-by-name lock the program and then the label, the same order as recording deletion (program, then cascaded associations), so they do not deadlock with it. Any remaining lock wait timeout or deadlock is returned as 409, which the client can retry. Unknown `{kind}` values return 404.

Collection and tag removal deletes metadata/associations only. It never removes a program, original recording or NAS artifact. Foreign keys cascade associations when an existing recording deletion removes its program, including both current mapper deletion paths. Read queries join existing programs so inconsistent legacy association rows cannot create broken recording entries. All organization changes are database-only; there is no NAS access or inferred series membership.

The web management page is `/collections`; recording detail pages assign/unassign collections and tags and can create a tag by name. Removal requires confirmation stating that recordings remain. Browse links use shared search with recording date ascending and ID ascending as the tie-breaker. Library search preserves `collectionId` and `libraryTagId` in the URL, combines them with other filters, and uses the same predicates for total count and page items. A saved filter for an already removed ID returns zero results.

API: `GET/POST /api/v1/library/{collections|tags}`, `GET/PUT/DELETE /api/v1/library/{kind}/{id}`, `PUT/DELETE /api/v1/library/{kind}/{id}/programs/{programId}`, `GET /api/v1/programs/{programId}/organization`, and `POST /api/v1/programs/{programId}/library-tags`. `GET /api/v1/programs` accepts `collectionId` and `libraryTagId`. Creation, rename and tag-by-name accept `{ "name": "..." }`. Mutations from the web use same-origin Next Server Actions. Existing deployment access controls still apply.
